VectorDB Engine

A lightweight, educational vector-search engine with a browser dashboard and a local Retrieval-Augmented Generation (RAG) workflow. Explore nearest-neighbour algorithms, compare search latency, inspect HNSW graph layers, and ask questions about documents using locally hosted Ollama models.
Project status: Educational prototype. Data and indexes are held in memory and are not persisted after the server stops.

Features
- Three nearest-neighbour approaches: Brute Force, KD-Tree, and HNSW.
- Multiple distance metrics: Euclidean, Manhattan, and cosine distance.
- Interactive dashboard: Search, insert and delete demo vectors; inspect results and timing.
- HNSW inspection: View graph/index information through the dashboard.
- Benchmarking: Compare the implemented search approaches using the same application.
- Document retrieval: Split documents into overlapping chunks and embed them locally.
- RAG question answering: Retrieve relevant document chunks and pass them as context to a local language model.
- JSON HTTP API: A Python backend communicates with the HTML/CSS/JavaScript frontend.

Important distinction: demo search vs. document search

The dashboard's demo search creates synthetic 16-dimensional vectors using keyword matching. These are useful for demonstrating and comparing search algorithms, but they are not semantic embeddings generated by an AI model.

The document workflow uses Ollama's nomic-embed-text model to generate text embeddings. Retrieved chunks are then sent as context to llama3.2 for answer generation.

Getting started

Prerequisites

- Python 3.8 or later
- Ollama for document embedding and RAG features
- The project files vectordb.py and index.html
  
1. Clone the repository
git clone <YOUR_GITHUB_REPOSITORY_URL>
cd <YOUR_PROJECT_DIRECTORY>
Replace the placeholders with your repository URL and directory name.
2. Download the Ollama models
ollama pull nomic-embed-text
ollama pull llama3.2
Ensure Ollama is running. On installations where it is not already running as a background service, start it in a separate terminal:
ollama serve
3. Start the application
From the directory containing vectordb.py and index.html, run:
python3 vectordb.py
Open the dashboard in your browser:

http://localhost:8080

The demo vector-search features can be explored without running the RAG workflow. Document embedding and question answering require Ollama and the models listed above.
How to use
1. Start the Python server.
2. Open http://localhost:8080.
3. Explore the demo dataset and select a search algorithm.
4. Compare Brute Force, KD-Tree, and HNSW results and timings.
5. Try the supported distance metrics and Top-K settings.
6. Use the document workflow to add text, retrieve relevant chunks, and ask a question about the available document content.
Exact controls depend on the current frontend implementation.

API overview

The backend exposes HTTP endpoints for vector search, document retrieval, index information, and status reporting.
Method	Endpoint	Purpose
GET	/	Serves the dashboard
GET	/search	Searches demo vectors
GET	/items	Lists demo vectors
GET	/benchmark	Returns search benchmark information
GET	/hnsw-info	Returns HNSW inspection data
GET	/doc/list	Lists document items/chunks
GET	/status	Reports Ollama status
GET	/stats	Returns demo database statistics
POST	/insert	Inserts a demo vector
POST	/doc/insert	Chunks, embeds, and inserts document content
POST	/doc/search	Retrieves relevant document content
POST	/doc/ask	Runs the RAG question-answering workflow
DELETE	/delete/{id}	Deletes a demo vector
DELETE	/doc/delete/{id}	Deletes a document item


For exact request and response fields, refer to the handlers in vectordb.py.
Core concepts demonstrated
- Vector embeddings: represent items as numerical vectors.
- Nearest-neighbour search: retrieve vectors closest to a query.
- Distance metrics: compare vectors using Euclidean, Manhattan, or cosine distance.
- Brute Force: exact baseline that evaluates every stored vector.
- KD-Tree: partitions a vector space to prune parts of some searches.
- HNSW: graph-based approximate nearest-neighbour search.
- Top-K retrieval: return the closest k results.
- Chunking: split longer documents into smaller overlapping text segments.
- Retrieval-Augmented Generation: retrieve relevant content and provide it to an LLM as context.
- HTTP and JSON: connect the browser interface to the Python backend.
- Concurrency: handle requests with a threaded HTTP server and protect selected operations with locks.
- Benchmarking: measure and compare search latency.

Current limitations

This project is designed for learning and experimentation, not as a production-ready database.
- In-memory storage: vectors, documents, and indexes are not durably persisted.
- Demo vectors are synthetic: demo search does not use semantic language-model embeddings.
- Approximate search trade-offs: HNSW speed and recall depend on index/query parameters and the dataset.
- KD-Tree metric assumptions: pruning correctness should be tested for each distance metric; the current pruning comparison is most directly justified for

Euclidean distance.
- Limited request validation: production use would require stronger validation of IDs, dimensions, numeric values, and request bodies.
- Security hardening needed: restrict permissive CORS settings and review network binding before exposing the service.
- Benchmark scope: timing results are illustrative; reliable evaluation should include repeated runs and recall/accuracy measurements.
- Local model dependency: document embedding and answer generation require Ollama and the configured models.

Potential improvements
- Add durable persistence and index recovery.
- Add automated unit and API tests.
- Validate vector dimensions, numeric values, Top-K values, and document chunking parameters.
- Compare HNSW recall@K against Brute Force ground truth.
- Run repeatable benchmarks across dataset sizes and dimensions.
- Improve API error handling, logging, and configuration.
- Restrict CORS and use a safer default host binding for local-only operation.
- Add document-source metadata and evaluate whether generated answers are supported by retrieved chunks.
